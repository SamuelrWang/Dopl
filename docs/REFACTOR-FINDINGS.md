## F-187 — Pending-auth store: renderer-driven slot pressure, and the records are plaintext

- Location: `dopl-desktop-app/main/auth.js:36` (`PENDING_AUTH_MAX = 4`), `:123-127` (`writePendingAuth` → `list.slice(-PENDING_AUTH_MAX)`, newest-wins eviction), `main/auth-store.js:9-12` (`new Store()` — plain `electron-store`, no `safeStorage`)

## F-189 — Closing a DM stopped being a LIVE event: the tombstone-hiding RLS policy makes its own CDC frame undeliverable (2026-08-10)

- Location: `supabase/migrations/20260810100000_channels_rls_hide_tombstoned.sql:202-213` (`channels_member_select`, the `AND deleted_at IS NULL` conjunct); `src/features/channels/server/repository.ts#softDeleteChannel` (the UPDATE that becomes invisible); `service-writes.deleteChannel` (the DM branch) and `service-workspace-departure.ts` (the departure branch) are the two callers
- Found during: post-apply reasoning about what C-15's policy change costs, in the same wave that applied it
- Severity: **bug (liveness regression, accepted for now)** — no data loss, no security consequence; the room is still correctly hidden, just not *promptly*
- Status: **open, ACCEPTED.** Shipped knowingly in `1d11a31`; recorded here so the trade is not rediscovered as a mystery.

**THE MECHANISM, WHICH IS THE WHOLE FINDING.** `channels` is in the `supabase_realtime` publication (verified: `channel_consent_requests`, `channel_members`, `channel_messages`, `channels`). Closing a DM is an **UPDATE** that stamps `deleted_at` — and `realtime.apply_rls` evaluates the **NEW** record against the subscriber's SELECT policy before delivering. That policy now requires `deleted_at IS NULL`. So the row the frame is announcing is, by the same statement that produced the frame, no longer visible to the subscriber, **and the frame is dropped.** The close was previously deliverable for exactly the reason §7 records about soft deletes generally: an `UPDATE` produces a full new record carrying `workspace_id`, so the `workspace_id=eq.<id>` filter matched and the doorbell rang. C-15 did not break the filter; it made the row fail the policy the filter is checked alongside.

**EFFECT:** the peer's sidebar keeps rendering a DM that is closed until their next refetch. Nothing is wrong on screen except the timing — `listChannels` filters `deleted_at IS NULL`, so the next read drops it correctly. **This is a downgrade from live to next-refetch, not a stale-forever bug.**

**⚠ THE OBVIOUS GENERALIZATION IS THE TRAP: this is a property of EVERY soft-delete-hiding SELECT policy, not of DMs.** Any table where (a) the tombstone is an UPDATE, (b) the table is in the publication, and (c) the SELECT policy excludes tombstones, has silently traded its delete doorbell for a refetch. `channels` is the only one in this codebase today because it is the only table that still soft-deletes AND is published — but the next `deleted_at IS NULL` added to a published table's policy inherits this for free and will not be noticed, because the failure is a frame that does not arrive.

**REMEDY SKETCHED, NOT TAKEN — and the ORDER is the whole design.** Touch the peer's `channel_members` row (a no-op `UPDATE`, e.g. re-stamping a column it already carries) **BEFORE** stamping the channel tombstone. `channel_members` is published and carries `workspace_id` in its replica identity (`20260807150000`, `REPLICA IDENTITY USING INDEX`), so that UPDATE rides the existing `CHANNEL_TABLES` / `SYNC_TABLES` doorbell both subscribers already refetch on. It **must** come first: `channel_members_member_select` was rewritten in the same migration to require `c.deleted_at IS NULL` on the parent channel, so the identical touch performed AFTER the tombstone is dropped for exactly the reason this finding opens with. A remedy for this bug is one statement away from being another instance of it.

**NOTE THE ASYMMETRY BETWEEN THE TWO CALLERS, because it is why this reads as "sometimes live".** The ordinary DM close (`deleteChannel`) writes only the `channels` UPDATE and is therefore fully dark. The **workspace-departure** close (`service-workspace-departure.ts`) also DELETEs the leaver's `channel_members` row, and a DELETE's deliverability turns on the subscription filter against `old_columns` (= the replica identity, which carries `workspace_id`) with `old_record` PK-redacted, rather than on a policy evaluation — so that path probably still rings the doorbell. **Reasoned from the deployed identity and §7's `apply_rls` note, NOT observed** — treat it as a hypothesis, and if you ever need it to be true, verify it against a live frame first. Same class of owed verification as F-190.

## F-222 — ui-sync watches ONE workspace, last-writer-wins, now that more than one window can ask (2026-08-18)

- Found during: Phase 10 of `docs/CHANNELS-V2-WIRING-PLAN.md`, widening the realtime doorbell to the app-window registry
- `main/ui-sync.js` holds ONE realtime channel, joined with `filter: workspace_id=eq.{watched}`, and `dopl:sync-watch` sets `watched` for whichever renderer called last. That was exactly right while there was one window
- With a POP-OUT open it is last-writer-wins: both windows normally view the same workspace (the pop-out is opened from the main window's own channel), so nothing is visible day to day — but **switching workspaces in the main window while a pop-out is open leaves the pop-out's workspace unwatched**, and the pop-out's transcript then stops updating with no error and nothing in its log. The renderer's registry filters incoming events by `workspaceId`, so the mismatched frames it does receive are dropped rather than misapplied — the failure is staleness, not wrong data
- Phase 10 did the cheap honest half: `watch()` now logs the transition by NAME (`the watched workspace MOVED while windows were open`) rather than making it silent, and `start()`'s docblock states the bound
- Proposed resolution: make `watched` a SET keyed by sender `webContents.id` and join one channel per distinct workspace (realtime binds one filter per table per channel, so a union is genuinely more than one channel — this is not a filter change). Bound it: the app-window budget is small, so the channel count is too
- ⚠ Do NOT "fix" it by dropping the `workspace_id` filter and letting the renderer sort it out. The filter is what keeps the CDC evaluation scoped, and the whole reason this feed exists is that per-component channels ate >80% of DB time
- Status: open

## F-224 — `check-doc-refs` had two blind spots, and the channels-v2 review walked through both (2026-08-18)

- Found during: the channels-v2 adversarial review, whose two largest classes of finding were BOTH invisible to the one gate that exists to catch exactly them (`node scripts/check-doc-refs.mjs`, INVARIANTS §14)
- **BLIND SPOT ONE — `.md` was not in `SOURCE_EXT`.** The file-reference and symbol-anchor regexes both build off that alternation, so a doc naming another doc was never checked in either form. The review found **42 live citations of `apps/desktop-ui/src/pages/channels-v2/MAPPING.md`** across ~20 source files and 4 docs, months-fresh in tone and pointing at a file DELETED at the Phase 12 cutover, all of them green
- ⚠ **AND FIXING THE EXTENSION DOES NOT FIX THE 42, WHICH IS THE SHARPER HALF.** `md` is in `SOURCE_EXT` now (this change), so a markdown path carrying a `:NNN` line number, or a markdown path carrying a `›` symbol anchor, are both checked now (spelled out rather than shown, because a literal example here would be checked too — the extension caught this entry's own first draft) — but **every one of those 42 was a BARE PATH**, no `:NNN` and no `›`, and a bare-path class is deliberately still not implemented: `its intent lived in a MAPPING.md next to it` is prose, and a checker with false failures gets switched off, which costs more than this gap. **So the class that actually rotted is still uncovered, and this entry is the record of that decision rather than of a fix.** Anyone building it should start from "a bare path inside a code span, in a live (non-`DATED_CAPTURES`) doc" and measure the false-positive rate before wiring it to an exit code
- **BLIND SPOT TWO — `F-NNN` ids were only ever scanned inside `docs/*.md`.** The review found **five source files citing `F-203` where they meant `F-206`** (`view-model-requested.ts`, `› .test.ts`, `transcript.tsx`, `› .test.tsx`, `bits.tsx`) plus a migration citing `F-201` where it meant `F-207`. **Class (d) is added here** — the same resolve-or-fail rule over `src/`, `packages/`, `apps/`, `dopl-desktop-app/`, `scripts/`, `supabase/`. Measured on the way in: **1577 files scanned, 420 F-id references outside `docs/`, 0 unresolved**, so it landed green rather than with a backlog (~0.3 s for the whole run)
- ⚠ **STATE THE CEILING SO NOBODY MISTAKES A PASS FOR A PROOF, and it is the SAME ceiling class (b) already had: this catches a DANGLING id, never a MIS-CITED one.** `F-203` is a live entry. Every one of the six mis-cites this finding exists because of **would still pass under the new class** — they were fixed by a human reading them, and the check would only have fired if `F-203` had been deleted as resolved. What class (d) buys is the OTHER direction: the log's convention is that a resolved entry is DELETED, so an id cited from code is one prune away from meaning nothing, and until now nothing noticed
- **The generalizable bit, and it is the reason to keep this entry after the code change:** a gate's SCOPE is a claim about where a class of rot can occur, and this one's scope had been inherited from its first day (`docs/*.md`, non-recursive) through three later hardenings that each widened what it checked and never re-asked WHERE. **A checker that is green over the wrong tree reads exactly like a checker that is green.**
- Fixed in this change: `md` in `SOURCE_EXT`; class (d) over the six source roots, with `dist/` skipped there and only there (generated output carries whatever its source carried, so an id in it is not a second claim); the run now prints the source-tree counts beside the doc counts, because a scope you cannot see in the output is a scope nobody re-asks
- Status: open (the two extensions LANDED; the bare-path class is measured, argued and deliberately NOT taken — that half is what stays open)


## F-226 — a per-file line cap is not a property either side of a MERGE can be checked for (2026-08-18)

- Found during: F-225's fix (the split that took `view-model.ts` back under the cap). **This entry is F-225's other half**, split off rather than deleted with it — the split closed the line count; nothing closed the way the line count got there
- **The mechanism, measured on F-225 with `git show <commit>:<path> | wc -l`:** `components/channels-v2/view-model.ts` was **416** at Phase 5 (`4daa2eba`), **427** at review-fix wave 1 (`b19b4fdc`) and **497** at wave 2 (`e35245e0`) — under cap at every one — and **508** at the wave-2 MERGE (`202935e4`), which took wave 2's additions on one side and the cutover/Phase-10 additions on the other. **Neither parent violated the cap and the merge result did**, so every branch tip was green and the tree was red
- **Why no gate saw it.** The `src/` half of the 500-line cap is enforced by eslint alone (INVARIANTS §1) and `size-check` in ci.yml covers `packages/` only, so the cap is only as reliable as somebody running lint on the MERGE RESULT. CI lints what it is given; the parallel-worktree workflow this repo now uses routinely produces a merge commit nobody lints before it lands
- **What would fix it:** lint the merge commit rather than the branch tip — a merge queue, or a required check that runs on the merge result. **The cheap interim is a habit, not a config:** `npx eslint .` immediately after any multi-worktree merge, before the merge is pushed. ⚠ Do NOT "fix" it with an `eslint.config.mjs` exemption; that list carries "DO NOT ADD TO THIS LIST — split the file instead"
- **The generalizable bit:** a per-file threshold — line cap, bundle budget, coverage floor — is checkable on a commit and NOT composable across a merge. Two changes that each fit can add up to one that does not, and every gate in the pipeline will have passed. Same class as F-224's lesson about a gate's SCOPE: green over the wrong tree reads exactly like green
- Status: open (process/CI; no code change closes it)
