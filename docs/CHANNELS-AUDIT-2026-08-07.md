## Tier 1 — Would not work / silent data loss

### C-1. The stale-threads cron sweeps **live** threads — ✅ RESOLVED (2026-08-08, F-171), and it was NOT marked here until this pass
*The route was rewritten. The clock now derives activity from `channel_messages` at READ time via a `channel_tasks_stale` RPC + one index, rather than from `channel_tasks.updated_at` — chosen over a trigger or a `postMessage` touch because it is O(open threads) read once a day instead of O(messages) written forever, and because it leaves `updated_at` with ONE honest meaning (which also kills the `set_thread_mode`-resets-the-clock half with no further code). C-17's NULL-author insert went with it. ⚠ ~~**The job has still never executed** — `CRON_SECRET` is unset~~ — **`CRON_SECRET` IS NOW SET AND LIVE (2026-08-10, verified: all three `/api/cron/*` answer 401 unauthenticated where they answered 503). THE SWEEP IS ARMED AND WILL EXECUTE FOR THE FIRST TIME.** The 14-day idle threshold, measured against a channel set the C-15 purge just rewrote, puts the first possible candidates around **2026-08-14** — a window, not a reprieve. The launch decision this bullet was flagging has been made by the environment changing; what is left is operational vigilance.*

`src/app/api/cron/stale-threads/route.ts:88-94` filters on `channel_tasks.updated_at`, and its own docblock (`:57-59`) claims this measures last activity. It doesn't: the only writer to that column is `updateTask` (`repository-tasks.ts:97-110`), reached solely from close / set_mode / reopen. `postMessage` bumps `channels.updated_at`, never the task row, and the migration has no trigger. So `updated_at == created_at` for any thread that was never closed.

**Effect:** a 15-day-old thread with hourly traffic gets a system card saying "no activity for a while." Conversely `set_thread_mode` resets the clock with zero activity. Currently inert — `CRON_SECRET` is unset in Vercel — which also means shipping a fix turns this on for the first time against a 14-day backlog.

### C-2. One ad-hoc session poisons the entire workspace's session-state push
Server contract: `SESSION_KEY_RE = /^[0-9a-fA-F-]{1,64}:[0-9a-fA-F-]{0,64}$/`, `threadId: z.string().uuid()` (`src/features/channels/schema-sessions.ts:44,72`), pinned by `schema-sessions.test.ts:87`. Producer violates it: an unthreaded inbound (the ordinary DM) yields `` `task-${channelId}-${seq}` `` (`dopl-desktop-app/main/targeting.js:257-260` → `trigger.js:68` → `session-spawner.js:224`), verified non-matching (`t`,`s`,`k` aren't hex).

**Effect:** one bad element fails the whole `sessions` array; 400 is non-retryable and the digest isn't recorded, so every later push fails too. While any ad-hoc session is live, `read_sessions` returns `[]` for that machine — *including valid UUID-threaded sessions in the same array* — and stale rows are never cleared. Neither suite crosses the boundary; the desktop's own fixture (`test/session-state-push.test.mjs:50`) would also be rejected by the server.

### C-3. The channel listener advances its **persisted** cursor before dispatching
`dopl-desktop-app/main/channel-listener.js:152-157` — `io.setCursor` (electron-store) runs before `dispatchMessage`. Every downstream early return is then a permanent silent drop: no Claude runtime (`trigger.js:106-109`), or `!created`, which is `null` on *any* network error or non-2xx from the consent POST (`consent.js:113-123`).

**Effect:** wifi drops for 15s during the consent POST → no consent row, nothing in Pending Requests, cursor already past the seq, restart re-awaits from the advanced cursor. The peer's agent long-polls forever. Flagged by the lifecycle auditor as the single highest-leverage fix in its report.

### C-4. A launch that never emits `system/init` jams its slot forever
`session-engine.js:331-365` — `startSession` sets `idleTimer: null` and never calls `scheduleIdle`; the timer is armed only by reducer effects requiring `launched`, dispatched only on `system/init`. A hung child sits at `phase:'launching'` with no watchdog; `hasLiveSession` stays true, every retry returns `{skipped:'busy'}`, the slot counts against `MAX_WINDOWS`, and no `task_started` was ever posted.

### C-5. Terminal states that post nothing — the requester's card pulses "Working…" forever
`session-effects.js:56-61` — `endLifecycle('abandoned')` returns `null`, so the 12h abandonment posts no message. Every other terminal reason posts (caps, operator End, close, crash). Same hole for the auth preflight hold (`session-engine.js:361-366` returns truthy, so `trigger.js:320-327` takes the success branch with no query ever run) and for eviction (`settle()` bypasses the reducer).

**Effect:** the *common* path — request → `task_started` → 15min idle → silent park → 12h → silent end — leaves the peer's UI claiming work in progress indefinitely. Parked records also reload as `'dormant'` and are skipped entirely (`session-engine.js:459-468`), so they're invisible on both ends.

**Effect:** agent proposes → human keeps it open → work continues → agent finishes and proposes again → swallowed. The stale prompt returns on reload, forever. The agent's only terminal act is permanently consumed by its first use. Compounded by C-1: the cron writes the same key first, so it can *steal* the agent's genuine proposal and replace its reason with "no activity for a while."

## Tier 2 — Containment and privilege

### C-10. A `full`-profile headless spawn gets **no containment at all**
`tool-profiles.js:220-222,252-254` — `buildDeniedTools`/`buildRestrictionArgs` short-circuit to `[]` for `full`. `session-spawner.js:291-298` therefore passes only `--mcp-config`: no `--allowedTools`, no `--disallowedTools`, no `--settings`, **no `--strict-mcp-config`**. The session processing an untrusted peer's message loads the operator's *global* MCP servers (Slack, Gmail, Supabase, every connector) and honours global `permissions.allow` unopposed.

The SDK lane already decided the opposite for the same profile name (`session-profiles.js:96-98,164` applies `SESSION_HARD_DENY` even under `full`). `full` is the **DB default** (`NOT NULL DEFAULT 'full'`), and the retirement test scopes its assertion to `RESTRICTED = ["read_only","dopl_only"]`, so the gap isn't covered.

### C-12. An agent can rewrite its own tool profile — ✅ RESOLVED (2026-08-10)

*Samuel's ruling: **the agent tool profile is a containment control, not a preference.** `PATCH /channels/[channelId]/members` is now `sessionOnly`, same wrapper option and same threat model as `PATCH /consent/[id]` and `POST|DELETE /trust`, with the attack written out in the route's docblock. Not an outage for the operator: desktop main authenticates with Supabase cookies and the bundled SPA with a Supabase access JWT, and only a `dopl_at_*` bearer takes the OAuth branch — nothing in `dopl-desktop-app/main` PATCHes this route at all, it only READS `myAgentToolProfile` off the channel DTO.*

*⚠ **One correction to the finding below, and it is the reason the gate could be the whole METHOD rather than a field.** The finding says the route "writes `agentToolProfile`", which understates the case: **since F-170 removed notify scope the route writes `agentToolProfile` and NOTHING ELSE** (`ChannelMemberSelfUpdateSchema`). The comment above `handlePatch` still described the notify-scope field and had been stale since F-170 — it is corrected in place. So per-method and per-field coincide here, which is exactly why C-13's visibility gate needed a different mechanism. **`GET` stays open (reading the roster decides nothing) and `POST`/`DELETE` — add / remove a member — are deliberately UNGATED, because invites are a separate decision (C-13's invite half).***

*⚠ **OPEN RESIDUAL, and it is Samuel's to rule on, not an oversight: `minRole` stays `viewer`.** A viewer setting their OWN agent's profile is defensible — the service enforces channel membership and always targets `ctx.userId`'s row — but nobody has decided it out loud, and "defensible" is not the same as "decided". Recorded so it is a standing question rather than a thing everyone assumes someone else settled.*

`src/app/api/channels/[channelId]/members/route.ts:75` — `PATCH` has no `sessionOnly` and defaults to `minRole: viewer`, and it writes `agentToolProfile`. Trust (`trust/route.ts:51-66`) and consent (`consent/[id]/route.ts:47-65`) are both `sessionOnly` with comments describing exactly this threat model. ### C-13. Agents can widen a channel's audience, unconfirmed — ⚠ VISIBILITY HALF CLOSED (2026-08-10); the INVITE half is DECIDED-OPEN, not forgotten

*✅ **The visibility half is fixed, and it introduced a new mechanism.** `PATCH /api/channels/[channelId]` refuses an agent (`dopl_at_*`) caller on the `visibility` field via `SESSION_ONLY_FIELDS` — **the first FIELD-level session gate in the codebase.** Why not the method: that PATCH is four writes behind one verb (`name`, `topic`, `visibility`, `archived`) and only one changes who can see the room; gating the whole method would spend an agent capability the ruling never asked for. **The rule this establishes, now in ENGINEERING §9: gate the METHOD by default, gate the FIELD when the method carries writes an agent may legitimately make.** The gate is direction-free — public→private is also an access change an agent should not make silently, `@dopl/client` has no channel-update method at all so no narrowing caller exists to break, and direction-free means the gate needs no read of the current row. ⚠ **A field gate is INVISIBLE to the method-level tripwire** (there is no `sessionOnly: true` in the file), so `write-gate-coverage.test.ts` grew a second pin asserting the field-gated set is exactly this route, that the constant names `visibility`, and that the handler actually reads `auth.agentTokenId` and throws `SESSION_REQUIRED` — a constant nothing reads would otherwise satisfy a file list while gating nothing.*

*✅ **The human half too**: `components/go-public-dialog.tsx` replaces the PATCH-on-click. The copy says plainly that every workspace member will be able to read the whole channel **including every message and thread already in it**, and that re-privatizing removes future access rather than what has already been read — the asymmetry this finding names. One direction only; `needsGoPublicConfirm` is what the host branches on, so "does this need a human?" and "what does the human read?" live in one file instead of being re-derived at the call site. **The server does not trust the dialog** — the field gate is the enforcement.*

*⚠ **THE INVITE HALF IS OPEN BY RULING (Samuel, 2026-08-10: invites stay as-is), which is a different status from unaddressed.** `POST`/`DELETE` on the members route are deliberately ungated and any member may still add anyone, with no consent card. Do not "finish" C-13 by gating invites — that would be reversing a decision, not completing a fix. If it is ever revisited, revisit it as a decision.*

Invite is a first-class MCP op (`channel-ops-open.ts:118`) and **any** member may add anyone (`service-writes-members.ts:40-55`); visibility private→public is `minRole: member`, not `sessionOnly` (`route.ts:48`). Neither raises a consent card. Note the asymmetry: raising a prompt is `sessionOnly`-protected; exposing the entire transcript to the workspace is not. The UI compounds it — `channels-view-core.tsx:332-342` PATCHes visibility immediately with no dialog, while delete (reversible for a DM) gets a full destructive confirm.

### C-15. RLS leaks what the API scrubs, and ignores `deleted_at` — ✅ RESOLVED, BOTH HALVES; migrations APPLIED to production 2026-08-10

*Samuel's ruling, in two parts: **permanently deleted means permanently deleted**, and **`role` / roster basics are public to the workspace while per-member SETTINGS are not.** Four migrations, all applied and verified pre- and post-apply by count.*

*✅ **The `deleted_at` half — `20260810100000`.** Five SELECT policies gained `deleted_at IS NULL`: `channels`, `channel_members`, `channel_messages`, `channel_tasks`, `channel_agents` (the child policies test the PARENT channel's tombstone via `EXISTS`, so a tombstoned channel takes its whole subtree out of view in one statement). **DM reopen is unaffected** — `reviveChannel` runs as service role, which RLS does not gate. `20260810110000` then purged the **19** pre-switch non-DM tombstones, behind an **executable** DM-survival guard rather than a comment promising one: **0 DMs existed and 0 were touched**, and had any existed the migration would have aborted rather than trusted its own `WHERE`.*

*✅ **The leak half — `20260810120000`, and the mechanism is the interesting part: it is a COLUMN PRIVILEGE, not a policy.** RLS filters rows; the requirement here is a column, so no policy could express it. The DTO scrub could not either — its docblock claimed "it holds for every path", which was false, because `channel_members` is in the realtime publication and `authenticated` held table-wide SELECT, so the raw row reached any channel member over CDC **and** over PostgREST with the anon key the browser ships. `REVOKE SELECT … FROM anon, authenticated` + a per-column `GRANT` of the public columns leaves `agent_tool_profile` **service-role-only**, which binds both consumers at once. **The standing rule for any new per-member setting: add it to `dto.mapMemberRow`'s scrub AND leave it out of that migration's GRANT list — two edits, and the second is the one that binds.** The scrub STAYS (defence in depth, and it shapes the API response, since the server reads as service role). **No new policy helper was added, deliberately:** `20260730052410` had to grant `anon` EXECUTE on the realtime RLS helpers, so every new helper is a fresh footgun on a surface that already has one.*

*⚠ **ONE ACCEPTED RISK AND ONE ACCEPTED REGRESSION, both filed rather than buried.** **F-190:** if the deployed `apply_rls` tests table-level SELECT ahead of its per-column loop, `channel_members` CDC goes dark for `authenticated` entirely — a lost roster doorbell, not a leak; one-statement rollback is in the migration header and **verification is owed at first live observation, by watching a frame, not by querying `information_schema`.** **F-189:** the tombstone-hiding policy makes the DM-close UPDATE's own CDC frame undeliverable (`apply_rls` evaluates the NEW record, which the statement just made invisible), so closing a DM is no longer a live event for the peer — next-refetch only. **That is a property of every soft-delete-hiding policy on a published table, not of DMs**, and the next `deleted_at IS NULL` added to a published table's policy inherits it silently.*

`dto.ts:185-210` nulls `notify_scope` / `agent_tool_profile` for everyone but the viewer, "so it holds for every path." RLS returns the whole row to any channel member (`20260725120000_channels.sql:180-192`), and `channel_members` is in the realtime publication — so who muted the channel and how tightly their agent is scoped is roster-public over CDC and from the browser console (`src/shared/supabase/browser.ts:27` ships the anon key). Separately, no channel policy filters `deleted_at` (`:152-160`, `:205-217`), so a "permanently deleted" channel's full transcript stays readable to members via PostgREST.

### C-20. Deactivated members stay addressable — ⚠ ADDRESSING + SWEEP HALVES CLOSED (2026-08-10); the orphaned-thread note is STILL OPEN

*✅ **THE SWEEP HALF IS CLOSED** (Samuel, 2026-08-10: "if someone leaves a workspace, it shouldn't just be a filter but they need to definitely be removed. Fully and cleanly removed"). `channels/server/service-workspace-departure.removeWorkspaceDepartedMember` deletes the leaver's `channel_members` row in every channel in the workspace, and is wired into `workspaces/server/membership-admin.removeMember` — **the ONLY app-level leave path there is.** It runs AFTER the membership delete and never before (running it first and then failing the delete would evict a still-active member from every room) and is best-effort, so a channels failure cannot 500 a workspace removal that already committed.
